風險一 · 人員與設備的單點依賴

六個服務裡有五個，能修改的原始碼只存在開發人員的筆電。 筆電故障或遺失時，線上服務會繼續運作，但沒有任何人能再修改它 —— 前端要重寫、容器要重建、建置設定會全部消失。

風險二 · 無法回溯

目前的上線方式是人工打包後上傳。因此以下問題目前都沒有答案：

  • 線上這一版是哪一份程式碼？
  • 上週三改了什麼？為什麼改？
  • 要退回上一個正常的版本，怎麼退？

風險三 · 沒有把關

從寫完程式到上線，中間沒有任何自動檢查。 近期有一個「使用者以為存檔成功、實際上資料沒寫入」的問題， 就是靠使用者回報才發現的。

重點

版本管控與 CI/CD 是兩件事。 版本管控解決風險一與風險二，已於 2026-08-17 完成； CI/CD 解決風險三，並讓上線變成可重複、有紀錄的動作。

架構GitHub 與 Azure 怎麼溝通

一次上線的五個步驟

1
開發者推送程式碼 改完程式後推上 GitHub。這一步同時就是備份與留下紀錄。
2
自動檢查 語法、建置、安全性掃描。有問題就在這裡擋下來，不會流到線上。
3
向 Azure 換取臨時通行證 GitHub 出示身分，Entra ID 驗明後發給一張數分鐘後就失效的通行證。
4
部署到對應的服務 只更新有變動的那個服務，其餘五個不受影響。
5
健康檢查 自動確認服務有正常回應。異常則標記失敗並通知，線上維持舊版。
安全性設計

GitHub 上不儲存任何密碼。 傳統做法是把一組固定密碼存在 GitHub 上，缺點是會外洩、會過期、要定期更換。 這次採用的方式是「出示身分、換取臨時通行證」—— GitHub 每次都拿它自己簽發的身分證明去換一張數分鐘有效的通行證， 沒有任何長期有效的密碼存在於系統之外。

使用者的登入密碼不在上述範圍內 —— 密碼由使用者自行設定、僅以不可還原的形式儲存於登入中心， 從未出現在任何程式碼或設定檔中。

現在能做到什麼

  • 筆電故障 → 任一台電腦取回程式碼即可繼續開發
  • 查得到每一次修改的內容、時間與原因
  • 要比對「上週和今天差在哪」是一個動作

帶來什麼前後對照

現在

  • 上線＝人工打包上傳，步驟靠記憶
  • 沒有任何自動檢查
  • 問題常由使用者先發現
  • 要退版幾乎做不到
  • 只有一個人做得到這件事

導入後

  • 上線＝按一次確認，流程固定
  • 語法、建置、安全性自動把關
  • 部署後自動確認服務正常
  • 退版＝重跑上一次成功的流程
  • 流程寫在檔案裡，任何人都執行得起來

對營運的四個實際好處

1
降低人員依賴 上線流程從「某個人知道怎麼做」變成「寫在檔案裡的步驟」。 人員請假、離職或交接時，系統仍然可以維護。
2
問題提早被發現 目前累積的自動化測試（含近期資料遺失問題的重現測試）可以接進流程， 在上線前執行。近期那個問題若有這道關卡，不會流到使用者手上。
3
出錯能快速復原 每次上線都對應一個明確的程式碼版本，退回上一版是標準動作， 不需要憑印象重建。
4
稽核與交接有依據 任何時間點都查得到「線上是哪一版、誰改的、為什麼改」。 未來若需通過內部或客戶的資訊安全查核，這是基本要求。
誠實說明限制

目前的方案不包含零中斷上線。每次部署服務會中斷約 10–30 秒， 原因是現行的服務方案不具備該功能，升級後每年約增加 500 美元。

評估結論：這些是內部工具，將部署安排在非上班時段即可， 建議暫不升級。日後若有對外服務的需求再評估。
