Netronix AI Bot 建置實錄

在一台 2017 年的 Intel MacBook Pro 上，把 Hermes Agent 裝起來、接上 ChatGPT Codex 的額度， 再串成一個會回話的 LINE Bot。這份文件記錄實際做了什麼、哪裡卡住、以及還沒解決的問題。

端到端已打通 Hermes v0.20.5 gpt-5.6-sol 白名單 2 人 通道為臨時網址 工具未鎖定

目前這套系統長什麼樣

一則 LINE 訊息從手機送出，到回覆出現在螢幕上，中間經過五個環節。其中一個是臨時的。

LINE 使用者發訊 → Hermes 收到 webhook → 白名單放行 → gpt-5.6-sol 推論 → 回覆送達手機， 整條鏈路實測通過。Gateway log 可見完整的 inbound message → response ready → Sending response 週期。

但還不能開放給大眾

目前 Agent 仍持有終端機與檔案讀寫權限，而進階指令掃描器（tirith）未安裝， 只有粗略的字串比對在把關。額度也綁在個人 ChatGPT 訂閱上。 在鎖定工具與切換計費方式之前，白名單不應該放寬。詳見「風險與決策」。

cryptography 的取捨

安裝過程中唯一需要人為決策的地方，而且牽涉到已知漏洞。

Hermes 的 pyproject.toml 硬性釘選 cryptography==50.0.0， 註解明確說明是為了修補多個漏洞：

  • CVE-2026-69247 — PKCS#7 EnvelopedData 的 Bleichenbacher oracle
  • GHSA-m2h6-j472-rp4c — 萬用字元 DNS 名稱可逃脫 permittedSubtrees
  • GHSA-jwv3-5hgf-82ww — 重複自簽中介憑證造成指數級路徑建構

問題是這個版本在 Intel Mac 上裝不起來：

版本macOS wheel可用於 Intel
50.0.0macosx_11_0_arm64否 — 僅 Apple Silicon
48.0.1macosx_10_9_universal2是 — 含 x86_64

上游從 50.0.0 起砍掉了涵蓋 Intel 的 universal2 wheel。剩下的路只有從原始碼編譯， 但那需要 OpenSSL 開發標頭與 Rust 工具鏈，這台機器兩者皆無。安裝腳本的四層 fallback 因此全數失敗。

已採取的決定

在知情的前提下，將 cryptography 降版至 48.0.1，接受上述三個漏洞。 判斷依據是受影響的程式路徑（企業微信、阿里雲請求簽名、GitHub App JWT） 在目前用途下不會被觸及。這是取捨，不是修好了。

本機修改，未來需留意

~/.hermes/hermes-agent/pyproject.toml 有兩行被改動（第 101 行與第 395 行）， 原始檔備份於同目錄的 pyproject.toml.orig。 hermes update 會自動 autostash 再套回，通常能保留； 但若某次更新後安裝失敗且錯誤指向 cryptography 編譯，先確認這兩行是否還在。

順帶修正的一個問題

安裝腳本把 PATH 寫進 ~/.bashrc，但 macOS 的 Terminal 開的是登入 shell， 只讀 ~/.bash_profile——而該檔案並不存在。照原樣使用者開啟終端機會找不到 hermes 指令。已建立標準的橋接檔（單行 source .bashrc），並實測確認可用。

用 ChatGPT 訂閱額度驅動 Agent

Hermes 對 Codex 有第一方支援，不需要 API key，也不需要任何第三方代理。

Hermes 內建 openai-codex provider，定義位於 plugins/model-providers/openai-codex/： 

openai_codex = ProviderProfile(
    name="openai-codex",
    aliases=("codex", "openai_codex"),
    api_mode="codex_responses",
    env_vars=(),  # OAuth external — no API key
    base_url="https://chatgpt.com/backend-api/codex",
    auth_type="oauth_external",
)

登入方式：獨立的裝置碼流程

Hermes 能讀取 Codex CLI 的 ~/.codex/auth.json，但原始碼明確建議另開獨立登入。 實際執行時它直接走了裝置碼流程，沒有詢問是否匯入——這正是期望的結果。

為什麼不共用憑證

OAuth 的 refresh token 是一次性的。若 Hermes 與 Codex CLI／VS Code 共用同一份 auth.json，兩邊會輪流讓對方的 token 失效，結果是雙方都時不時掉登入。 獨立 session 各自持有憑證，用的仍是同一份訂閱額度。

登入與驗證的完整指令

登入是裝置碼流程，需在瀏覽器完成授權，終端機會停在 Waiting for sign-in... 輪詢。

# 1. 發起 OAuth 登入（會印出網址與一組裝置碼）
$ hermes auth add openai-codex --type oauth

To continue, follow these steps:
  1. Open this URL in your browser:
     https://auth.openai.com/codex/device
  2. Enter this code:
     XXXX-XXXXX

Waiting for sign-in... (press Ctrl+C to cancel)
Added openai-codex OAuth credential #1: "openai-codex-oauth-1"

此時要在瀏覽器做的四件事

終端機會停在 Waiting for sign-in... 持續輪詢。這是正常的， 不要按 Ctrl+C。換到瀏覽器完成授權：

  1. 開啟裝置授權頁

    網址是 https://auth.openai.com/codex/device。 若終端機沒有自動開啟瀏覽器，複製該網址自行貼上。

  2. 輸入終端機顯示的代碼

    格式為 XXXX-XXXXX，中間的連字號要一起輸入。

  3. 用有付費訂閱的 ChatGPT 帳號登入

    Codex 額度需要 Plus／Pro／Business 方案，免費帳號沒有。 登入的帳號決定之後 Hermes 會消耗誰的額度。

  4. 在授權確認頁按同意

    完成後終端機會自動繼續，Waiting for sign-in... 變成 Added openai-codex OAuth credential #1。

代碼有時效

裝置碼大約十分鐘後失效，過期就要重跑 hermes auth add openai-codex --type oauth 取得新的一組。 所以發起指令後就直接完成授權，不要中途去忙別的事。

若詢問是否匯入現有憑證

當畫面出現 Found existing Codex CLI credentials at ~/.codex/auth.json — Import these credentials? [y/N] 時，回答 n。 OAuth refresh token 是一次性的，共用同一份檔案會讓 Hermes 與 Codex CLI／VS Code 互相使對方的 token 失效。

為什麼一定要用 hermes model 而非直接改設定

預設設定的 base_url 指向 OpenRouter。若只用 hermes config set model gpt-5.6-sol 改模型名稱， provider 與 base_url 不會跟著換，結果是拿著 Codex 的模型名稱 去打 OpenRouter，必然失敗。互動選單會把三項一起設定。

速度：一個被誤判的問題

最初測得 48 秒，一度以為是推理強度設太高。實測後證明不是。

minimal7s暖機後，同一個問題

三種強度差異幾乎不存在。那 48 秒是首次執行的冷啟動成本—— 載入套件、skills、抓取模型清單。當次紀錄顯示 0 tool calls，模型並未做額外動作。

對 LINE Bot 的實際意義

Gateway 是常駐服務，不會每則訊息重啟，因此不需承擔冷啟動成本。 實測 LINE 端回應落在 6.4 至 9.8 秒，遠低於 LINE plugin 的 45 秒慢速門檻， 使用者會直接收到回覆，不會退化成「先給按鈕再點開」的體驗。

實際執行的步驟

  1. 在 LINE Developers Console 建立 Provider 與 Channel

    到 developers.line.biz/console/，用 LINE 帳號登入，然後：

    • 建立 Provider——就是一個組織容器，名字隨意（本例為 NetronixAI）
    • 在該 Provider 底下建立 Messaging API channel
    • 填基本資料：bot 名稱、頭像、類別

    別選成 LINE Login——那是網站登入用的，不會產生 bot。 必須是 Messaging API。

    過程中會要求填「隱私權政策」與「服務條款」網址，兩者都標示（選填），測試階段留空即可，日後隨時能補。

  2. 在 Official Account Manager 關閉自動回應

    到 manager.line.biz → 設定 → 回應設定：

    項目設定原因
    自動回應訊息停用否則使用者收到的是 LINE 罐頭訊息，不是模型回答
    聊天停用bot 模式不需要人工客服介面
    加入好友的歡迎訊息可留不影響運作
    Webhook此時仍鎖住需先填 Webhook URL 才會解鎖，見步驟 6

  3. 取得兩把金鑰

    回到 Developers Console，進入你的 channel，兩把金鑰分別在不同分頁：

    金鑰位置取得方式
    Channel secret Basic settings 分頁 往下捲，在 Channel ID 下方，約 32 位英數字，旁邊有複製鈕
    Channel access token Messaging API 分頁 捲到最下面，找到 Channel access token (long-lived)，按 Issue 發行，約 170 字元

    Access token 屬長期有效、不會過期。若遺失可按 Reissue 重發， 但舊的會立即失效，需同步更新 .env 並重啟 gateway。

    兩者最終寫入 ~/.hermes/.env（權限 600）。

  4. 設定 Gateway

    執行 hermes gateway setup 選擇 LINE，它會逐項詢問：

    提問怎麼答
    LINE channel access token貼上長 token（密碼欄位，畫面不會顯示任何字，貼完直接 Enter，別重複貼）
    LINE channel secret貼上 32 位 secret，同樣不顯示
    Webhook port / hostEnter 用預設（8646 / 全介面）
    Public HTTPS base URL留空。這格是給 bot 傳圖片、語音、影片用的，不是 webhook 網址，純文字問答用不到
    Allowed user IDs先留空——此時還不知道自己的 LINE user ID，見步驟 7
    Allow all users?留空或 false，切勿設 true
    Slow response thresholdEnter 用預設 45 秒
    Start the gateway now?Y
    開機自動啟動為 launchd 服務？測試階段建議 n（但見踩坑 05——此回答未必生效）

  5. 架設公開通道

    LINE 的伺服器必須主動連進你的 Mac，但家用網路在 NAT 後面。 通道工具提供一個公開 HTTPS 網址，把請求轉進本機 8646。

    選 cloudflared 而非 ngrok，因為它的快速通道免註冊帳號， 且有免安裝的執行檔可下載（本機無 Homebrew）。 

    $ cloudflared tunnel --url http://localhost:8646

+------------------------------------------------------+
|  https://<隨機單字>.trycloudflare.com              |
+------------------------------------------------------+

    這個視窗要保持開啟，關掉通道就斷。

  6. 回填 webhook 網址並解鎖開關

    Developers Console → Messaging API 分頁 → Webhook settings：

    1. Webhook URL 填 https://<通道網址>/line/webhook ——結尾的 /line/webhook 一定要有，只填域名會失敗
    2. 按 Update
    3. Use webhook 開關 → 打開
    4. 按 Verify，應顯示 Success
    5. 回 OA Manager 的「回應設定」，先前灰掉的 Webhook 開關此時已解鎖 → 打開

    兩個後台都要開 Webhook，只開一邊不會運作。 OA Manager 的開關必須等這裡填好 URL 才會解鎖，這是順序限制而非故障。

  7. 設定白名單

    Hermes 預設拒絕未知寄件者，所以第一次發訊會被擋——這是防護正常運作。 被拒絕的同時，log 會記下對方的 user ID，這正是加入白名單所需要的。 

    # 1. 請對方加好友並發一句話，然後撈出 user ID
$ grep -o "U[0-9a-f]\{32\}" ~/.hermes/logs/gateway.log | sort -u

# log 中的原始樣貌：
#  LINE: rejecting unauthorized source
#  {'type': 'user', 'userId': 'Uxxxxxxxx…'}

# 2. 寫進 .env（多人用逗號分隔，不可有空格）
$ echo 'LINE_ALLOWED_USERS=U第一位,U第二位' >> ~/.hermes/.env

# 3. 重啟後等 40 秒（見踩坑 02）
$ hermes gateway restart && sleep 40 && hermes gateway status

    目前 2 人。每新增一人都要重複這套流程並重啟服務， 這是尚未解決的規模化瓶頸——解法見「風險與決策」的 pairing 模式。

六個實際卡住的地方

記錄成因與解法，避免重建時重蹈覆轍。其中一個是本次協作中我給出的錯誤指示。

01

白名單設了卻無效

症狀
hermes config get 讀得回值，但 gateway 仍拒絕訊息。
成因
hermes config set 把值寫入 config.yaml，但 adapter.py:740 用的是 os.getenv("LINE_ALLOWED_USERS", "")——只讀環境變數，永遠看不到 config.yaml。
解法
改寫入 ~/.hermes/.env，重啟 gateway。
註記
這是 Hermes 設定介面的不一致：它照單全收、也讀得回來，讓人以為設定成功。本次協作中我最初給出的就是錯誤的 config set 指示，導致多繞了一段。
02

重啟後 30 秒內訊息會遺失

症狀
重啟 gateway 後立刻測試，訊息毫無反應，log 連拒絕紀錄都沒有。
成因
舊程序尚未釋放 8646，新程序綁定失敗：[Errno 48] address already in use。Hermes 會在 30 秒後自動重試並成功，但那段空窗期 LINE 推送過來會直接失敗，訊息就掉了。
解法
每次 hermes gateway restart 後等約 40 秒，並以 hermes gateway status 確認已連線再測試。
03

Webhook 開關無法打開

症狀
OA Manager 的「回應設定」中，Webhook 開關呈灰色點不動。
成因
並非故障，而是順序限制。必須先在 Developers Console 填入 Webhook URL，該開關才會解鎖。
解法
先架好通道拿到公開網址 → 填入 Developers Console → 再回 OA Manager 開啟。
04

安裝腳本的依賴階段全數失敗

症狀
四層 fallback 逐一失敗，venv 完全是空的，hermes 指令不存在。日誌只顯示 pip 輸出的開頭，看不到真正錯誤。
成因
cryptography==50.0.0 在 Intel Mac 無預編譯 wheel，改從原始碼編譯時因缺少 OpenSSL 開發標頭而失敗。
解法
以 uv pip install --override 降版至 48.0.1，並修改本機 pyproject.toml 讓安裝腳本能跑完後半段。
05

launchd 選項未依回答生效

症狀
對「是否開機自動啟動」回答 n，但服務仍被安裝，且會自動啟動。
成因
產生的 plist 中 RunAtLoad 與 KeepAlive 皆為 true，與回答相反。
解法
目前選擇保留（後續本來就需要常駐）。若要移除：hermes gateway uninstall。
註記
值得留意的是，這代表開機時會自動跑起一個 bot。在工具尚未鎖定前，這件事本身就是風險。
06

金鑰被貼入對話紀錄

狀況
Channel secret 與 access token 被貼進協作對話中。
影響
兩者因而存在於本機的純文字對話紀錄檔（~/.claude/projects/…/*.jsonl），並隨對話傳送至 API。原本它們只存在於 LINE 後台與權限 600 的 .env。
建議
於 Developers Console 執行 Reissue，舊金鑰即刻失效，紀錄中的字串隨之作廢。
現況
使用者已知悉並選擇不重發，維持現有金鑰運作。此處記錄以備日後決策參考。
07

看起來卡住，其實是收到按鈕沒點

症狀
問「今天股票大盤跌幅」後遲遲沒有答案，以為 bot 掛了。
成因
該問題需要查資料，Agent 連續做了 6 輪 API 往返，耗時 57.7 秒，超過 LINE plugin 的 45 秒門檻（LINE_SLOW_RESPONSE_THRESHOLD）。免費 reply token 撐不了那麼久，Hermes 因此改送一顆「點我看答案」的按鈕氣泡——答案其實早就備妥，只是要點開。
判斷方法
看 log 的 api_calls。等於 1 表示直接回答；大於 1 表示 Agent 動用了工具，時間會顯著拉長。
解法
維持現狀（觸發率低）；或設 LINE_SLOW_RESPONSE_THRESHOLD=0 停用按鈕、一律改用 Push API 直送（但 Push 訊息計入 LINE 方案的免費額度）；或關閉查資料的工具。
08

連「1+2」都要十幾秒

實測
1+2 → 耗時 17.4 秒、api_calls=2、回覆長度 1 字元（就是「3」）。
成因
這是 agent 架構的固有成本，不是故障。Hermes 被設計成「會拿工具做事的人」，因此連簡單算術都可能先評估要不要用工具，多花一輪 API。加上 gpt-5.6 屬推理模型，本來就會先思考再回答。
實測下限
純對話約 2.5 至 9.8 秒，不會再快。答案太短時容易讓人以為沒收到。
最有效的加速
關閉不需要的工具（hermes tools 或聊天中 /tools），讓 api_calls 穩定在 1。調整 agent.reasoning_effort 的效果有限——實測 minimal／low／medium 在簡單問題上差距不到 2 秒。

開放給大眾之前必須先解決的事

目前的白名單模式無法規模化，但直接放寬會同時放大三個風險。

風險一 · Agent 持有這台電腦的控制權

Hermes 預設帶終端機執行、檔案讀寫、程式執行等工具。開放給不特定使用者， 等於讓陌生人透過打字間接操作這台 Mac。這不需要對方有惡意—— 誘導 LLM 執行危險指令（prompt injection）是已知且活躍的攻擊面。

而 gateway 啟動時已出現警告：tirith security scanner enabled but not available， 代表進階指令掃描器未安裝，目前只有粗略的字串比對在把關。

風險二 · 額度綁在個人訂閱上

每一則訊息都在消耗個人 ChatGPT 訂閱的 Codex 額度。額度用盡時， 本人的 Codex 也會一併停擺。目前沒有任何用量上限或分帳機制， 亦無法區分是誰用掉的。

風險三 · 服務不具持續性

cloudflared 快速通道的網址在重啟後即失效，一失效就必須回 LINE 後台重新填寫。 且服務綁在一台 2017 年的筆電上——闔上蓋子、睡眠、或斷網，bot 就下線。

存取模式的三個選項

Hermes 的 dm_policy 支援 open / allowlist / pairing / disabled。差別在於「誰決定誰能進來」。

模式誰決定可規模化適用情境
allowlist你，逐一手動否目前狀態；少數固定成員
pairing使用者自助是公司同事、已知社群
open無人把關是僅在工具完全鎖定後才可考慮
另建輕量後端由你設計是對外公開產品

關於第四個選項

若目標是做給不特定多數人使用的產品，Hermes 這種「個人 agent」的架構本來就不是為此而生。 它的價值在於持有你的工具與權限；把它開放給大眾，等於把最大的優點變成最大的風險。 該情境下更合適的做法是直接以 LINE Messaging API 撰寫輕量後端接 LLM， 不讓一個擁有機器控制權的 agent 暴露在公開入口。

建議的執行順序

順序有意義：前一項未完成前，不應進行下一項。

  1. 鎖定工具

    執行 hermes tools（需互動終端機），關閉終端機執行、檔案讀寫、Computer Use，僅保留純對話與必要的網頁查詢。

    這一步未完成前，不要放寬任何存取限制。

  2. 改用 API key 計費

    hermes auth add openrouter --type api-key。用量可控、可設預算上限，且不再牽連個人 ChatGPT 訂閱——額度被灌爆時損失的是可控的金額，而不是自己的工作工具。

  3. 切換為 pairing 模式

    使用者自助配對加入，你不需逐一處理，同時保留一道門檻擋掉機器人與隨機流量。

  4. 處理服務持續性

    固定網域取代臨時通道；若要長期營運，將 Hermes 移至雲端主機，而非依賴一台無法升級系統的筆電。

尚待確認

以個人 ChatGPT 訂閱額度轉供第三方使用，是否符合 OpenAI 的服務條款， 本報告無法代為判斷，建議在擴大使用者範圍前自行確認。

階段三 · 修復 Intel Mac 的依賴失敗

Apple Silicon 不會遇到這段，可整段跳過。

安裝腳本的四層依賴 fallback 會全數失敗。先取得真正的錯誤訊息：

$ cd ~/.hermes/hermes-agent

確認是不是 wheel 缺失

$ curl -s https://pypi.org/pypi/cryptography/50.0.0/json | python3 -c "

改 pyproject 讓安裝腳本能跑完後半段

安裝腳本是在依賴階段倒下的，後面的 PATH 設定、skills、Playwright、cua-driver 都沒執行。 把版本釘選改掉後重跑一次，讓它自己完成。

    -e 's/^  "cryptography==50\.0\.0",/  "cryptography==48.0.1",/' \
    -e 's/^  "cryptography>=50,<51",/  "cryptography==48.0.1",/' \

$ git diff --stat                            # 應為 2 insertions, 2 deletions

這是取捨，不是修好

降版重新引入 CVE-2026-69247、GHSA-m2h6-j472-rp4c、GHSA-jwv3-5hgf-82ww。 hermes update 之後若安裝失敗且錯誤指向 cryptography 編譯， 先檢查 git diff pyproject.toml 這兩行是否還在。
