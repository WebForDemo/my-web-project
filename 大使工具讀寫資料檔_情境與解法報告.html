AI 應用商店 · 上架架構

大使的工具要讀寫資料檔,上架後怎麼辦?

上架情境只有兩種;需要共用資料的那一種,再分成四個成熟度階段。 大使幾乎不必改程式。

2026-08-17 · 技術限制均為實測

概覽先問一句話

情境 一

不需要與他人共用

  • 稅額計算、抽籤、QR Code
  • 把我自己的 Excel 丟進來算報表
  • 查對照表(純查詢,不累積紀錄)
✓ 現在就能上架
情境 二

需要與他人共用

  • Project Code 發號(不能撞號)
  • 共用料號主檔、客戶清單
  • 大家一起維護的檢驗規範
→ 分四階段,見「四個階段」
最常見的誤解

「大家拿到同一個檔案」不等於「資料互通」。 資料寫在 HTML 裡的工具,所有人看到的內容一樣 —— 那是同一版影印本。 你在自己那本上寫一筆,別人那本不會出現。

判斷要按「資料」不是按「工具」

一支工具可能同時有兩種資料。只要有任何一份需要共用,整支就按情境二處理。

成本

整件事不需要新增任何 Azure 資源,不花錢。沙箱與其他五個系統一律不動。

運作方式情境二怎麼運作

為什麼大使不用改程式

商店在中間接手工具的讀檔與存檔動作。工具照原本的寫法跑, 拿到的卻是伺服器上那份共用資料;它以為存到本機,實際上存回了伺服器。

共同編輯的四道防護

Excel 是整份檔案,不像資料庫可以一列一列改,所以同時編輯必須處理:

#防護效果
1版本檢查存檔時比對版本,不符就明確拒絕,絕不靜默覆蓋
2誰在編輯的提示有人開著時其他人看得到;是提醒不是強制鎖
3自動留舊版保留最近 10 版,誤覆蓋一鍵還原
4不自動合併商店不懂內容語意,硬合併會產生假資料 → 後存的人重做一次
對照

把 Excel 放共用網路磁碟時問題一模一樣而且更糟 —— 那時候是靜默覆蓋,沒人知道。 搬到商店至少會擋你、告訴你、還留有備份。

附錄白話 ↔ 技術

討論時的說法實際是什麼
「每個人一本自己的筆記本」瀏覽器的 localStorage,各自獨立、互不相通
「牆上的公用白板」伺服器上的共用檔案或資料表
「同一版影印本」資料寫在 HTML 裡 —— 內容一致,但寫入不互通
「攔截」在工具程式跑之前,先換掉它讀檔／存檔用的函式
「後存的人要重做」樂觀鎖:比對版本號,不符就拒絕

四個階段成熟度階梯

階段做得到做不到誰要動
第 0 階
單檔 HTML		 算完就走的工具;使用者自己丟檔案進來 任何共用都不用
第 1 階
zip 下載		 功能完整、可離線、資料不出公司 線上同步。每個人手上是他下載那天的版本,而且沒有機制通知他有新版 都不用
第 2 階
＋ 資料檔		 所有人讀到同一份最新資料;更新只要換檔;可共同編輯;可下載成 Excel; 留舊版可還原;權限到檔案級(誰看得到、誰能寫) 列級權限(「只能看自己那幾列」);伺服器端計算與報表; 整檔覆寫 → 兩人同時存,後者要重做 商店

第 3 階
＋ 資料庫		 列級新增修改不會互相覆蓋(發號結構上不可能撞);列級權限; 誰改了哪一筆的稽核;報表與 ERP 串接 — 商店
每支各一次
第 1 階有個容易誤會的地方

zip 裡如果是「HTML ＋ 資料檔」,對方解壓後雙擊是讀不到那個資料檔的(瀏覽器的安全限制)。 所以第 1 階能跑的形態是:資料內嵌在 HTML 裡,或讓使用者自己選檔案。 真正的分離要到第 2 階才成立。

什麼時候該往上升一階

  • 第 1 階 → 第 2 階:開始有人拿到舊資料;或資料一個月更新一次以上。 升級成本低 —— 把資料抽出來 ＋ 十幾行載入器
  • 第 2 階 → 第 3 階:真的發生撞號或覆蓋事故;需要「誰改了哪一筆」的稽核; 需要只給部分人看部分資料;要跟 ERP 對接。 升級成本中高,而且每支工具各做一次 → 不要規劃「全部都要到第 3 階」

實例NTX Project Code 編碼產生器

這支工具很有代表性 —— 它同時需要兩個不同階段。

那份資料適合階段理由
規則表 188 筆第 2 階偶爾由維護者更新,其他人只讀 → 用共用檔案就夠
歷史料號 186 筆第 2 階同上
新開的申請紀錄第 3 階 要防撞號、要知道是誰開的 → 必須列級
不處理的話會發生什麼

李工程師 09:00 核發 E60Q32,只寫進他自己的瀏覽器。
翁工程師 09:20 選一樣的規格,工具查的還是內建那份 —— 不知道 20 分鐘前發生了什麼 —— 於是也核發 E60Q32。同一個代碼發給兩個專案。

最省工的做法

混合:規則與歷史走第 2 階(共用檔案),申請紀錄走第 3 階(資料庫)。 比整支升到第 3 階省很多工,而撞號問題一樣解決。

資料已經抽出來了

用工具自己的匯出功能撈出來的,原始檔一個 byte 都沒動:

檔案內容餵回工具驗證
完整更新包 JSON規則 188 筆 ＋ 歷史 186 筆,25 個欄位齊全 零差異
發布檔 xlsx兩張表(規則／歷史),給人用 Excel 看 118 筆有細微差異
歷史 CSV 單獨匯入—工具本身有 bug,匯入失敗

→ 所以程式要讀的用 JSON,xlsx 只給人看。 另外做了一份「讀外部資料版」的 HTML(副本,不是原檔),已實測:改資料檔畫面就跟著變。

要不要資料庫檔案 vs 資料庫，差在哪

一句話：檔案是「一份文件」，資料庫是「一個櫃台」。 文件可以人手一份影本；櫃台只有一個，所有人排隊，由櫃台決定誰先誰後。

這次真的踩到了：編碼產生器

兩位同事都開著編碼產生器的頁面，各自要申請一個新料號：

時間發生什麼問題在哪
09:15A 和 B 分別打開工具 —— 各自拿到一份當下的影本—
09:40A 建立 E00620，存檔成功—
09:41B 也建立 E00620，畫面同樣顯示「建立成功」 B 的影本裡沒有 A 那筆，查不出重複
09:55B 重新整理，才發現 E00620 是 A 的，自己那筆不見了 白做工，而且中間那段時間他以為號碼是他的
關鍵

平台擋住了資料被覆蓋（A 的號碼完好無損，B 的沒有寫進去）， 這部分是對的。做不到的是在 B 按下建立的當下就告訴他 —— 因為那個檢查發生在 B 自己的電腦裡，而他手上是一份舊影本。

資料庫能做到、檔案做不到的五件事

#能力白話什麼時候會需要
1唯一性保證 兩個人同一秒申請同一個號碼，資料庫保證只有一個會成功 料號、工單號、專案編號
2只改其中一筆 檔案是整份一起寫，兩個人改不同列也會互相擋；資料庫可以只動自己那一筆 多人同時維護同一張表
3寫入時附條件 「庫存不可以扣成負數」這種規則，由資料庫在寫入當下把關 庫存、額度、金額
4查得動 幾十萬筆裡找一筆、做統計報表，不必整份讀進瀏覽器 資料量大、要出報表
5多系統共用 ERP、BI、其他系統可以接同一份真實資料，不必各自複製一份 跨部門、跨系統

代價差在哪

檔案（現在）資料庫
誰能做大使自己，用 AI 幾小時就能生出來 要有人設計資料表與介面，是開發工作
上線速度當天就能上架以天／週計，且要排進開發順序
改需求大使自己改，改完重新上架要回頭找開發改
同時操作不會弄錯資料，但後做的人要重做一次 當下就擋，不會有人白做工
適合部門級小工具 —— 目前約九成的情境 涉及唯一編號、庫存、金額、跨部門的少數幾支
判斷準則

這份資料如果兩個人同時改，會不會產生「錯誤的事實」？

不會 —— 會議記錄、交接筆記、點檢表、清單 → 檔案就夠了， 最壞的情況是有人要重做一次。
會 —— 兩個專案拿到同一個料號、庫存被扣兩次、同一筆錢付兩次 → 需要資料庫，因為錯誤會流到公司外面去。

現在的狀況與建議

項目狀態
資料不會被默默覆蓋✅ 已經做到 —— 後存的人會被明確擋下，並保留最近 10 個版本
存檔失敗會明確告知✅ 已經做到 —— 跳出必須處理的提示，不會讓人以為存好了
資料被別人更新會提醒✅ 已經做到 —— 工具上方會出現橫幅提示重新載入
按下當下就擋住重複❌ 做不到 —— 這需要資料庫，目前暫不執行
目前的作法

編碼產生器這類發號工具，先用一條規矩頂著： 重新整理後還看得到的號碼才算數，不要在那之前把號碼給客戶或寫進文件。

要升級成資料庫版本的話，就這一支工具而言不是大工程 —— 一張資料表、一個介面、工具本身改幾行，估計一天內可以完成。 等這類工具變多、或撞號真的造成損失時再做即可。

實作清單第 2 階段各自要做什麼

一 · 大使要做的

先看這支工具原本是哪種起點,要做的事差很多。

起點 A · 資料本來就寫在 HTML 裡NTX 那種

#要做的難度
1把資料抽出來成一個檔(xlsx / csv / json 都行) 低 —— 用工具自己的匯出功能就有
2程式改成啟動時讀那個檔,而不是用內建資料 約十幾行
3保留內建資料當後備(讀不到就用內建) 建議做 —— 本機雙擊才不會壞
4壓成一個 zip 上傳(index.html ＋ 資料檔)低
5上架表單選「需要共用」＋「誰可以修改」低

起點 B · 本來就是「HTML ＋ 資料檔」

#要做的難度
1確認用的是相對路徑 ./資料檔.xlsx通常一行
2壓成一個 zip 上傳低
3上架表單選「需要共用」＋「誰可以修改」低
兩種起點都一樣

讀寫的程式邏輯完全不用改,不用學 API、不用碰資料庫。
但兩件事一定要遵守:不要引用 CDN(程式庫一起放進 zip)、 不要寫死本機絕對路徑。

二 · 商店要做的

A · 上架與儲存

1接受 zip 並解開 —— 找出 index.html 當主程式,其餘存成「這個工具的資料檔」
2資料檔存到專屬位置;每次覆寫前先把舊版留起來,保留最近 10 版
3上架表單新增兩個欄位:「需要共用資料嗎」、「誰可以修改」

B · 記帳(資料本體仍在檔案裡)

4新增一張表:工具、資料檔名、目前版本號、大小、最後修改者、修改時間
5記錄誰正在編輯(開著工具時定時回報,逾時視為離開)
6工具本身加兩個設定:是否共用、誰可以寫

C · 兩個通道核心

7讀檔通道 —— 工具讀相對路徑時,接到伺服器上那份唯一的檔
8存檔通道 —— 攔下工具的「下載存檔」動作,改成上傳覆蓋伺服器那份
9存檔時比對版本號:相符才覆寫並 +1;不符明確拒絕

D · 權限

10讀:沿用現有的可見範圍(看得到這個工具的人才讀得到資料)
11寫:依上架時選的設定擋掉沒權限的人
12只讀模式下按存檔要明確提示「這份資料是唯讀的」

E · 使用者看得到的介面

13工具上方一條狀態列:檔名 · 版本 · 最後由誰於何時更新 · 目前幾人開啟
14兩顆鈕:下載這份資料檔、重新載入
15存檔成功 →「已更新共用資料(版本 N)」;衝突 →「已被 XXX 更新,請重新載入」

F · 後台

16工具管理裡可以直接替換資料檔(維護者不必重新上架整個工具)
17看版本歷史、還原舊版

三 · 最小可行版本

想先上線一半的話,只做 1、2、4、7、10、12、13 這七項,就得到唯讀共用:

做完之後
所有人讀到同一份最新資料✓
維護者換檔就更新,不必重新上架工具✓
資料檔可下載、留有舊版✓
從工具裡改資料(按存檔會被明確擋掉)✗
為什麼建議先做這一半

它解決了「有人拿到舊資料」這個最常見的問題,而且風險最低 —— 沒有覆寫就沒有衝突,不必處理同時編輯。剩下的是「共同編輯」那一半,可以等真的有需要再做。

# 角色
你是前端工程師，要為「Netronix AI 應用商店」開發一支單檔網頁小工具。
這個平台有嚴格限制，請完全遵守下方「平台規範」，不得變通。

# 一、我要做的工具（我填）
1. 工具用途：______________________（例：發票稅額換算、會議抽籤）
2. 誰會用：________________________
3. 工具要做什麼：__________________
4. 資料從哪來：
   □ 不需要資料      □ 資料量很小，直接寫在程式裡
   □ 使用者每次自己挑檔案／拖檔案進來（xlsx / csv / json / txt / pdf）

# 二、平台規範（請勿更動）
A. 只交出**一個檔案**：index.html。不要拆成多個 js / css 檔。
B. **完全不連外**：不得使用 CDN、Google Fonts、外部圖片或任何 http(s) 網址。
   需要的程式庫請**直接內嵌**，或改用瀏覽器原生 API：
     · CSV / TXT → 自己寫解析（TextDecoder 可用）
     · JSON      → JSON.parse
     · XLSX      → 用 DecompressionStream('deflate-raw') 解 zip 後讀 sheet XML
     · PDF       → 平台不能用 <embed>/<iframe> 顯示 PDF，Web Worker 也被禁用。
                   只能：①提供「下載」按鈕　②內嵌 pdf.js 並關閉 worker、畫到 canvas
C. 要讓使用者提供檔案時，用 <input type="file"> 或拖放，**不要**去讀固定路徑。
D. 要讓使用者把結果存下來時，**只能**用：
   產生 Blob → URL.createObjectURL → <a download> 觸發下載。
   不要用 showSaveFilePicker，不要呼叫任何伺服器 API。
E. **不要依賴 localStorage 保存重要資料**（平台可能不給用）。
   若要用必須 try/catch 包住，而且不能是唯一的保存手段。
F. 介面：繁體中文、系統內建字型、支援深淺色（prefers-color-scheme）、手機可用。

# 三、交付內容
1. index.html 完整原始碼
2. **自我檢查清單**，逐條回答「是／否」並附證據：
   □ 只有一個 index.html？
   □ 全檔沒有任何 http:// 或 https:// 的外部資源？
   □ 沒有引用 CDN 程式庫？
   □ 沒有絕對路徑（C:\ 之類）？
   □ 存檔是用 Blob + a download？
   □ 沒有把 localStorage 當唯一保存手段？

# 二、平台規範（請勿更動）
A. 交出**兩個檔案**，檔名固定：
     index.html      ← 程式
     data.<副檔名>   ← 資料（例 data.xlsx、data.csv、data.json、data.pdf）
   **資料不要寫死在 HTML 裡**，一定要獨立成檔。
B. 讀資料一律用 fetch('./data.xlsx') 這種**相對路徑**。
   絕對不要出現 C:\Users\... 這種本機路徑。
C. 一定要做「讀不到就退回內建範例資料」的處理：
       let data = BUILTIN_SAMPLE;
       try { data = await loadFrom('./data.xlsx'); } catch (e) { /* 用內建 */ }
   理由：使用者可能直接雙擊 HTML，那時瀏覽器不給讀外部檔，工具必須照樣能開。
   畫面上請顯示目前用的是「外部共用檔」還是「內建範例」。
D. 存檔**只能**用這一種方式：
   產生 Blob → URL.createObjectURL → <a download> 觸發下載，
   而且下載的檔名要與來源相同（data.xlsx）。
   不要用 showSaveFilePicker，不要呼叫任何伺服器 API，不要用 fetch 上傳。
E. **完全不連外**：不得使用 CDN、Google Fonts、外部圖片或任何 http(s) 網址。
   需要的程式庫請**直接內嵌**，或改用瀏覽器原生 API：
     · CSV / TXT → 自己寫解析（TextDecoder 可用）
     · JSON      → JSON.parse
     · XLSX      → 用 DecompressionStream('deflate-raw') 解 zip 後讀 sheet XML
     · PDF       → 平台不能用 <embed>/<iframe> 顯示 PDF，Web Worker 也被禁用。
                   只能：①提供「下載這份 PDF」按鈕
                         ②內嵌 pdf.js 並關閉 worker、畫到 canvas
F. **不要依賴 localStorage 保存重要資料**（平台可能不給用）。
   若要用必須 try/catch 包住，而且不能是唯一的保存手段。
   使用者的成果要靠「存回 data 檔」保存，不是靠瀏覽器記住。
G. 介面：繁體中文、系統內建字型、支援深淺色（prefers-color-scheme）、手機可用。
H. 只用單一個 index.html，不要拆成多個 js / css 檔。

# 三、交付內容
1. index.html 完整原始碼
2. data.<副檔名> 範例檔（含 3～5 筆示範資料）
3. 「資料檔欄位說明」表格 —— 讓維護者知道怎麼用 Excel 編輯
4. **自我檢查清單**，逐條回答「是／否」並附證據：
   □ 資料有獨立成 data 檔，沒有寫死在 HTML？
   □ 讀取用相對路徑 ./data.xxx？
   □ 有「讀不到就用內建範例」的後備，而且畫面看得出用的是哪一份？
   □ 存檔是用 Blob + a download，檔名與來源相同？
   □ 全檔沒有任何 http:// 或 https:// 的外部資源？
   □ 沒有引用 CDN 程式庫？
   □ 沒有絕對路徑（C:\ 之類）？
   □ 沒有把 localStorage 當唯一保存手段？

各種資料格式怎麼處理

格式在平台裡的做法難度
csv / txt自己寫解析,不需要任何程式庫最簡單
jsonJSON.parse 一行搞定最簡單
xlsx用瀏覽器原生的 DecompressionStream 解 zip 再讀 sheet —— 不需要 SheetJS中等
pdf🔴 平台不能用 <embed> 顯示 PDF,Worker 也被禁 → 只能「提供下載按鈕」或「內嵌 pdf.js 並關閉 worker」較麻煩
圖片只允許 data: 與 blob: —— 圖片請轉成 base64 內嵌中等

檔名規則

檔案規定
index.html程式一律用這個名字
data.xlsx 等資料檔一律叫 data. ＋ 副檔名。不要用中文檔名 —— 不同系統與瀏覽器對中文檔名的處理不一致,容易讀不到
上傳時兩個檔壓成一個 zip(壓縮時不要多包一層資料夾)
AI 最常犯的三個錯,拿到成品先檢查這三項

① 偷偷引用 CDN —— 搜尋原始碼裡有沒有 https://,有就是錯的
② 把資料寫死在 HTML 裡 —— 範本 B 一定要有獨立的 data 檔
③ 用了 showSaveFilePicker —— 存檔必須是「觸發下載」那種寫法

Prompt 最後那份自我檢查清單就是為了逼 AI 自己回答這幾點。 如果它沒有逐條回答,直接叫它「請補上自我檢查清單」。
