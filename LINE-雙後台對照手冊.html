LINE 雙後台對照手冊

同一個 LINE 官方帳號，卻有兩個管理後台。它們不是新舊版本，也不是主從關係—— 而是同一個帳號的兩種視角，各管一半。搞清楚哪件事在哪邊做，能省下大量鬼打牆的時間。

Official Account Manager Developers Console 一個帳號，兩個入口

一個帳號，兩個入口

使用者加為好友的只有一個帳號。兩個後台看的是同一個東西，只是各自負責不同的面向。

Official Account Manager

manager.line.biz

  • 給行銷、客服、營運人員用
  • 不需要任何程式知識
  • 大多數 LINE 官方帳號只用這個

Developers Console

developers.line.biz/console

  • 給工程師用
  • 金鑰、webhook、API 設定
  • 只有要串接系統時才需要

為什麼要分成兩個

因為 LINE 官方帳號本來就不一定要接 API。

餐廳、零售、診所這類使用者只想群發優惠券、設個圖文選單、看看好友數， 完全不碰程式。對他們來說 Developers Console 是多餘的複雜度。

所以 LINE 把「開店做生意」和「串接系統」拆成兩個介面。 Messaging API 是額外啟用的能力，不是預設就有。

綁定關係

一個 Messaging API channel 對應一個官方帳號，一對一。 當初在 OA Manager 點「設定 → Messaging API → 啟用」的那一步， 就是把既有的官方帳號綁進 Developers Console 的某個 Provider 底下。

找不到某個設定時，先查這張表，通常是走錯後台。

兩套權限互不相通

把同事加進 OA Manager 的「權限管理」，不代表他能進 Developers Console； 反之亦然。要讓人同時能做兩邊的事，兩邊都得加。

Webhook 開關為什麼點不動

這是最常見的卡關點。它不是故障，是順序限制。

實際踩過的狀況

在 OA Manager 的回應設定看到 Webhook 開關是灰的、怎麼點都沒反應。 頁面下方其實已經寫了原因： 「如需操作Webhook，請在Messaging API的設定畫面中設定Webhook網址。」

而填 URL 需要一個公開的 HTTPS 位址，所以真正的順序是： 先架好通道 → 填 URL → 才回來開開關。

自動回應訊息會蓋掉你的 Bot

另一個重疊陷阱，症狀是「使用者收到罐頭訊息，不是我的回覆」。

回應設定項目接 Bot 時該設成不設會怎樣
自動回應訊息停用使用者收到罐頭訊息
聊天停用進入人工客服模式
加入好友的歡迎訊息可留不影響 bot 運作
Webhook啟用訊息不會轉送到你的伺服器

從零到收得到訊息

綠色是 OA Manager 的步驟，藍色是 Developers Console。注意兩邊是交錯進行的。

  1. OA Manager 建立官方帳號

    用 LINE 帳號登入 manager.line.biz，建立官方帳號，填名稱、頭像、類別。

  2. OA Manager 啟用 Messaging API

    設定 → Messaging API → 啟用。過程中要選或建一個 Provider（組織容器，名字隨意）。

    這一步就是把帳號綁進 Developers Console。隱私權政策與服務條款欄位為選填，測試階段可留空。

  3. OA Manager 調整回應設定

    設定 → 回應設定：關閉「自動回應訊息」與「聊天」。此時 Webhook 開關仍是灰的，正常。

  4. Developers 取得兩把金鑰

    Channel secret 在 Basic settings；Channel access token 在 Messaging API 分頁最下方按 Issue。

    兩把鑰匙任何人拿到都能冒用你的 bot，請當作密碼保管。

  5. 架設公開 HTTPS 位址

    LINE 的伺服器必須連得進你的機器。本機開發需要通道工具（cloudflared、ngrok）或有公網 IP 的主機。

  6. Developers 填入 Webhook URL

    Messaging API → Webhook settings → 填完整路徑並按 Update，接著打開 Use webhook，按 Verify。

  7. OA Manager 打開 Webhook 開關

    回到回應設定，先前灰掉的開關現在已解鎖，打開它。兩邊都開，訊息才會送達。

  8. 加好友實測

    用任一後台的 QR code 加好友並發訊息。收不到就照下一頁排查。

記住這條規則就不會迷路

要金鑰、設 webhook → Developers Console。
改外觀、關自動回覆、看數據 → Official Account Manager。
唯一的例外是 Webhook 開關，兩邊都要開。

免費就能做 Bot，但要看清楚計費的是什麼

Messaging API 本身不收錢，收費的是訊息則數。 而關鍵在於：不是每一則訊息都會被計算。

三種方案（台灣，未稅）

方案月費免費訊息超量加購
輕用量 NT$0 200 則／月 不可加購
中用量 NT$800 3,000 則／月 不可加購
高用量 NT$1,200 6,000 則／月 可加購，NT$0.2/則起（階梯計價）

中用量的陷阱

中用量不可加購。3,000 則用完就是用完，只能等下個月， 或當月升級到高用量。要做量大的推播，直接評估高用量比較實際。

真正的重點：回覆免費，推播才計費

這是整頁最重要的一段。搞懂它，200 則的免費額度可以撐很久。

訊息類型API計費什麼時候會用到
Reply 回覆 /v2/bot/message/reply 免費 使用者發訊後數十秒內回覆
Push 推播 /v2/bot/message/push 計 1 則／人 主動通知、reply token 過期後補送
Multicast 群發 /v2/bot/message/multicast 依人數計 一次發給多人
Broadcast 全體廣播 /v2/bot/message/broadcast 依好友數計 OA Manager 的群發功能

計費單位是「人」不是「訊息物件」

一次 API 請求最多可帶 5 個訊息物件。發給一個人時， 那 5 則只算 1 則。所以要傳圖文並茂的長回覆， 塞在同一個請求裡比分次送划算得多。

對純問答 Bot 的意義

好消息

只回答使用者提問的 bot，幾乎不會用到付費額度。 因為每一次回覆都是使用者先發問觸發的，走的是免費的 reply 路徑。 輕用量方案（月費 0 元）就足夠——那 200 則是留給「主動推播」用的。

會燒掉額度的三件事

1. 把慢速門檻設成 0。 Hermes 的 LINE_SLOW_RESPONSE_THRESHOLD=0 會停用按鈕機制、 一律改用 Push 補送。回應慢的問題會變成每題扣 1 則額度， 輕用量方案 200 則很快見底。

2. 排程主動通知。 cron 任務主動發訊息一定是 Push，全部計費。

3. 群發公告。 100 個好友發一次 = 100 則。

另一個獨立的軸：帳號認證

跟方案費用無關，常被混為一談。

狀態差別
未認證（一般帳號） 灰色盾牌。功能完整，但不會出現在 LINE 的搜尋結果，只能靠 QR code 或連結加好友
已認證（認證帳號） 藍色盾牌。可被搜尋到，曝光度較高。需送審，審核公司資料

認證與否不影響訊息計費，也不影響 Messaging API 能不能用。 內部使用的 bot 通常不需要認證——反而不出現在搜尋結果比較安全。

價格資訊的時效

以上為 2026 年台灣地區方案，未稅。LINE 調整過數次計價， 實際費用請以 OA Manager 的「帳務專區 → 推廣方案」為準。

LIFF：能跑在 LINE 裡、而且知道你是誰的網頁

LIFF 是 LINE Front-end Framework 的縮寫。 它不是特殊的 App 格式，本質上就是你自己寫的網頁—— 只是多了兩件一般網頁做不到的事。

一般網頁LIFF
使用者身分 不知道你是誰，要註冊登入 直接取得 LINE user ID 與名稱
開啟方式 跳出 LINE 開瀏覽器 在 LINE 內開，體驗不中斷
回到聊天室 做不到 可把訊息送回原對話
金流 自行串接 可接 LINE Pay
程式放哪 兩者都在你自己的伺服器上。LINE 不提供執行環境。

同一組 user ID

LIFF 取得的 userId，跟聊天機器人在 webhook 收到的 U 開頭那串是同一個識別碼。 所以 bot 與 LIFF 網頁能認出是同一個人——這是把「LINE 帳號」綁到 「你系統裡的會員」的鑰匙。

以點餐系統為例

常見的誤解是「把系統搬到 LINE 上」。實際上系統完全沒有搬家。

為什麼點餐不用純對話做

同一件事，兩種做法的落差。

實際怎麼做一個 LIFF

  1. 寫一個網頁

    React、Vue、純 HTML 都可以，你原本會的技術即可。放在有 HTTPS 的位址上。

  2. Developers 在 LIFF 分頁註冊

    填入網頁網址、選顯示尺寸，它會給你一個 LIFF ID。

  3. 網頁裡引入 SDK 並初始化

    await liff.init({ liffId: "你的-LIFF-ID" });

const profile = await liff.getProfile();
profile.userId       // Ubbd58c5a…　跟 webhook 收到的同一個
profile.displayName  // 使用者名稱

    剩下就是一般的網頁開發。

  4. 設定進入點

    通常在圖文選單放一顆按鈕，或在對話中送連結。網址格式：

    https://liff.line.me/{你的 LIFF ID}

開發成本的落差很大

對話機器人接上 Hermes 幾乎不用寫程式；LIFF 沒有現成方案， 是一個完整的前端開發專案。除非確實有「需要填表單」的需求， 否則先用對話把價值做出來，比較划算。

用指令自己查，不要靠目視

後台顯示的狀態未必等於實際狀態。以下三段可以直接定位問題在哪一環。

一、你的伺服器活著嗎

# 本機直接測
$ curl -s -o /dev/null -w "HTTP %{http_code}\n" \
     http://127.0.0.1:8646/line/webhook/health

二、外面連得進來嗎

$ curl -s -o /dev/null -w "HTTP %{http_code}\n" \
     https://<你的通道>/line/webhook/health

# 200 = 通　　000 = 通道斷了　　404 = 路徑錯

三、LINE 那邊登記的是什麼

這是最有價值的一招——直接問 LINE 的 API，比在後台肉眼確認可靠：

$ curl -s -H "Authorization: Bearer <CHANNEL_ACCESS_TOKEN>" \
     https://api.line.me/v2/bot/channel/webhook/endpoint

{
    "endpoint": "https://….trycloudflare.com/line/webhook",
    "active": true
}

endpoint 對不上就是網址過期了，active: false 就是開關沒開。 兩個欄位一次告訴你設定端的狀況。

未簽章的請求應該被拒絕

直接對 webhook 發一個沒有簽章的 POST，正確的行為是回 401。若回 200，代表你的伺服器沒有驗證 HMAC 簽章—— 任何人都能偽造訊息，這是必須修的漏洞。
